# 고용24 현행 공개 채용정보 수집 범위 감사

- 감사일: 2026-09-23 (Asia/Seoul)
- 범위: 비로그인 공개 UI, 현행 `work24.go.kr` 검색/상세와 레거시 `work.go.kr` 분리
- 실행 제한: 현행 목록 화면 확인, 현행 상세 5건만 확인. 전체 수집 미실행
- 개인정보: 채용 담당자 성명·전화·이메일은 수집 대상과 산출물에서 제외

## 1. 도메인별 robots.txt

### `https://www.work24.go.kr/robots.txt`

확인한 `User-agent: *` 관련 원문:

```text
User-Agent: *
disallow: /cm/common/
disallow: /sa/
disallow: /ei/
disallow: /cm/f/c/0100/selectUnifySearchPost.do
```

파일 첫머리에 `Allow: /`와 Sitemap이 있으나 `User-agent`보다 앞선 지시이므로,
허용 판정은 그 줄에 기대지 않고 `User-agent: *` 그룹의 불허 접두사와 대상 URL을
대조했다. 다음 네 대상은 어느 불허 접두사에도 매칭되지 않아 허용된다.

| 대상 | 판정 | 근거 |
|---|---|---|
| `/wk/a/b/1200/` | 허용 | `User-agent: *`의 Disallow와 불일치 |
| `/wk/a/b/1500/` | 허용 | 동일 |
| `/wk/a/b/1200/retriveDtlEmpSrchList.do` | 허용 | 동일 |
| `/wk/a/b/1500/empDetailAuthView.do` | 허용 | 동일 |

### `https://www.work.go.kr/robots.txt`

레거시 도메인의 `User-agent: *` 그룹에는 다음 규칙이 있다.

```text
User-Agent: *
Disallow: /empInfo/
...
Allow: /
```

따라서 `work.go.kr/empInfo/...` 상세는 차단이다. 이 규칙을 다른 오리진인
`work24.go.kr/wk/...`에 적용하지 않는다.

## 3. 공개 검색 요청 구조

현행 검색 초기 페이지와 페이지 2 이동을 실제 브라우저에서 확인했다.

- 결과는 서버 렌더 `text/html`이다. 결과 목록용 별도 JSON endpoint는 관찰되지 않았다.
- 검색 폼 `#mForm`: `POST /wk/a/b/1200/retriveDtlEmpSrchListInPost.do`
- 브라우저의 최종 canonical/pagination URL: `GET /wk/a/b/1200/retriveDtlEmpSrchList.do?...&pageIndex=2`
- 페이지네이션: `pageIndex`; 화면 함수는 `fn_Move(n)`에서 값을 설정한다.
- 지역: `region`, 법정 지역코드를 `|`로 결합한다.
- 창원 5개 구: `48125|48127|48123|48121|48129`
- 등록일: `regDateStdtParam`, `regDateEndtParam`; UI가 하이픈을 제거한 `YYYYMMDD`
- 구인인증번호: 목록의 상세 링크 query `wantedAuthNo`
- 상세 식별: 기존 WorkNet 공고는 `infoTypeCd=VALIDATION`,
  `infoTypeGroup=tb_workinfoworknet`

검색 화면은 타 채용 제공처 공고도 섞는다. 기존 2,045건 보강에는
`tb_workinfoworknet` 상세만 사용해 출처 의미가 달라지지 않게 한다.

## 4. 기존 2,045건 감사와 호환성

- 행 2,045, 구인인증번호 고유 2,045, ID 중복 0
- source URL 2,045/2,045, 수집시각은 단일 snapshot
- 동일 `normalized_company + title_raw + reg_date` 조합은 4그룹 8행이나 ID가 서로
  다르므로 ID 중복으로 삭제하지 않는다.
- 재게시 후보 표시는 21행이며 실제 중복 삭제와 구분한다.
- 저장된 필드 전체의 이메일/전화 정규식 후보 0행
- `cert_raw=[인증]`은 2,045건 모두 인증 표식이며 자격면허가 아니다.
- `occupation`과 `recruitment_count`는 2,045건 모두 비어 있다. 원 수집 경로가
  레거시 센터 목록뿐이었기 때문이다.
- 상세 5건의 join 성공은 5/5다. 기존 ID를 보존하고 별도 상세 보강 테이블을
  append-only로 만들 수 있다.

기존 `work24_analysis_ready.csv`를 덮어쓰지 않는다. 현행 보강은 별도 snapshot에서
`wanted_auth_no`로 결합한 뒤 검증된 필드만 processed 산출물에 반영해야 한다.

## 5. 결론과 다음 게이트

현행 `work24.go.kr` 상세는 robots 기준 허용되고 비로그인 공개 필드도 충분하다.
따라서 기술적으로는 모집인원·직종·직무내용·자격면허·고용형태·상세주소 보강이
가능하다. 다만 현재 약관은 대량 이용을 별도 계약 대상으로 두므로, 이번 단계의
5건 샘플을 넘어 전체 2,045건을 자동 요청하지 않았다.

`src/evidence/collection/work24_current.py`는 다음을 강제한다.

- 매 실행 시 두 도메인 robots 재확인
- 403/429 즉시 전체 중단, 재시도 없음
- 단일 순차 요청, 2초 최소 간격, 5xx/네트워크 오류만 제한적 exponential backoff
- 감사 명령 최대 10건, 전체 수집 CLI 미제공
- 담당자 개인정보 영역 미파싱, 직무내용 연락처 재마스킹
- 파일을 쓰지 않는 기본 감사와 기존 ID 기반 상세 URL 생성

전체 보강 전에는 한국고용정보원에 연구 목적의 대량 이용 범위·속도·재배포 조건을
확인하고, 승인된 범위가 생기면 별도 append-only 저장 명세와 재개 캐시를 추가한다.
